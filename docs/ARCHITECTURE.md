# アーキテクチャ・アルゴリズム詳細

## 1. 全体パイプライン

```
File(jpg/png/HEIC)
  → [HEIC判定時] heic2any でJPEG化
  → createImageBitmap → Canvasへ縮小描画(長辺1024px)
  → MediaPipe Face Landmarker で478点ランドマーク検出
  → グレーワールド仮定によるホワイトバランス補正(ImageData)
  → ランドマークから額/両頬/顎/髪/瞳のサンプリング領域を算出
  → 各領域の代表色をロバスト統計(中央値+外れ値除去)で抽出
  → RGB→Lab / RGB→HSV 変換
  → 特徴量化(Warm/Cool, Value, Chroma, Contrast, Saturation, Lightness)
  → ルールベース分類器で4シーズン + スコア内訳を算出
  → 結果画面へ描画
```

実装の対応関係:

| ステップ             | ファイル                                     |
| -------------------- | -------------------------------------------- |
| HEIC変換             | `src/core/heic.ts`                           |
| 画像読み込み・縮小   | `src/utils/image.ts`                         |
| 顔検出               | `src/core/faceLandmarker.ts`                 |
| 照明補正             | `src/core/lightingCorrection.ts`             |
| 領域抽出             | `src/core/regionExtraction.ts`               |
| 色サンプリング       | `src/core/colorSampling.ts`                  |
| 色空間変換           | `src/core/colorSpace.ts`                     |
| 特徴量抽出           | `src/core/featureExtraction.ts`              |
| 判定                 | `src/core/classifier/ruleBasedClassifier.ts` |
| オーケストレーション | `src/core/imagePipeline.ts`                  |

## 2. なぜこの技術構成か

- **OpenCV.js不使用**: MVPで必要な処理(領域内ピクセルの統計、ホワイトバランス)はCanvas2D+自前TSで十分。OpenCV.js(8〜10MB)を追加する代わりに、モバイルでの初期ロード速度を優先した。将来、髪領域のセグメンテーション精度を上げる際の拡張候補として温存。
- **TensorFlow.js不使用**: 顔検出はMediaPipeが担当し、分類はルールベース(将来はONNX Runtime Web)で完結するため不要。
- **MediaPipeアセットの自己ホスト**: `@mediapipe/tasks-vision`はデフォルトでCDNからWASM/モデルを取得する設計だが、本サイトは「画像だけでなく通信そのものを外部に出さない」ことを重視し、ビルド時(`scripts/prepare-assets.mjs`)に`public/`へ配置して同一オリジンから配信する。

## 3. 領域抽出(regionExtraction.ts)の考え方

MediaPipe Face Mesh(468/478点)の公開キーポイントマップに基づき、額・左頬・右頬・顎それぞれについて「肌が写っている可能性が高い代表点群」をあらかじめ定義し、その重心を中心に円形領域を取る。円の半径は目頭外側同士の距離(顔スケール)に比例させることで、写真の解像度・顔の大きさに依存しない安定したサイジングを実現している。

髪色は、Face Meshが生え際より上を追跡しない制約があるため、額最上点からさらに上方向へ顔の高さに応じて外挿してサンプル領域を推定する近似手法を採る(前髪で隠れている場合は精度が下がることをUI上で警告する)。

瞳色は478点モデルに含まれる虹彩ランドマーク(468〜477番)を利用する。

## 4. 色抽出のロバスト性(colorSampling.ts)

領域内のピクセルから、白飛び(反射ハイライト)・黒つぶれ(影)を除外したうえでチャンネルごとの中央値を代表色として採用する。中央値は平均よりも産毛の陰影・ほくろ・メガネの反射といった外れ値に強く、少数の異常画素に結果が引っ張られにくい。

## 5. 照明補正(lightingCorrection.ts)

グレーワールド仮定(「画像全体のRGB平均は理想的には無彩色に近いはず」)に基づくホワイトバランス補正を実装。オレンジ照明・青白い照明など、光源色による肌色の偏りを軽減する。極端な写真で色が破綻しないよう補正ゲインは0.6〜1.6倍にクランプしている。

## 6. 特徴量とシーズン判定の理論的根拠

4シーズン理論(標準的なパーソナルカラー診断理論)における各シーズンの定義:

| シーズン         | 暖色/寒色 | 明度   | 鮮やかさ |
| ---------------- | --------- | ------ | -------- |
| Spring(イエベ春) | 暖色      | 明るい | クリア   |
| Summer(ブルベ夏) | 寒色      | 明るい | ソフト   |
| Autumn(イエベ秋) | 暖色      | 深い   | ソフト   |
| Winter(ブルベ冬) | 寒色      | 深い   | クリア   |

これを3次元の特徴量空間(warmCool, value, chroma / それぞれ-1〜+1)にマッピングし、各シーズンの理想座標とのユークリッド距離をsoftmaxで正規化してスコアとする(`ruleBasedClassifier.ts`)。

- **warmCool**: 肌のLab色相角(`atan2(b*, a*)`)。黄み寄り(暖色)ほど角度が大きく、赤紫寄り(寒色)ほど小さいという経験則に基づく。
- **value**: 肌のLab明度(L*)を主とし、髪の明度があれば7:3で加重平均。
- **chroma**: 肌のLabクロマ(`sqrt(a*²+b*²)`)。
- **contrast**: 肌と髪(または瞳)の明度差。Phase2の12タイプ細分化で活用予定。

これらのピボット/レンジ定数(`featureExtraction.ts`内)は経験則による暫定値であり、臨床的に検証されたものではない。Phase3でラベル付きデータが集まり次第、統計的にキャリブレーションし直すことを想定している。

## 7. 分類器の抽象化と将来のAI化(Phase3)

`src/types/index.ts`の`Classifier`インターフェース、`src/core/classifier/`配下の構成により、特徴量抽出(`featureExtraction.ts`)までのパイプラインは変更せずに、分類器だけを差し替えられる設計にしている。

```ts
interface Classifier {
  classify: (features: FeatureVector) => ClassificationResult;
}
```

Phase3では、ラベル付きデータ(正解シーズンが分かっている写真の特徴量ベクトル)を収集し、数百KB程度の軽量MLPをONNX形式で学習・エクスポートし、`OnnxClassifier`として同インターフェースを実装する形を想定している。ONNX Runtime Web自体もWASM/WebGLでブラウザ内推論が可能なため、「無料・サーバーレス・オンデバイス」という制約を維持したままAI化できる。

## 8. Phase2: 12タイプへの拡張方針

4シーズンの判定に加え、`contrast`(コントラスト)と`chroma`の詳細な閾値を使い、各シーズンを3タイプ程度に細分化する(例: Spring → ライトスプリング/ブライトスプリング/クリアスプリング)。既存の特徴量ベクトルに新規軸を追加する必要はなく、閾値テーブルの拡張で対応可能な設計にしている。

## 9. 制約と精度に関する誠実な説明

- 本診断はルールベースであり、機械学習モデルによる高精度なパーソナライズ判定ではない。
- 照明条件・カメラの色特性・写真の圧縮などにより結果が変動しうる。
- 領域抽出は「MediaPipeランドマーク上の代表点」に基づく近似であり、解剖学的に厳密な境界ではない。
- これらの理由から、結果画面には常に「判定の根拠」(スコア内訳・抽出色)を提示し、ユーザーが結果を鵜呑みにせず参考情報として捉えられるようにしている。
